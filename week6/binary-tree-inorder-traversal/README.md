Моё решение - рекурсивное. Создаю список result и вспомогательный метод traverse, который принимает узел и этот список. В методе сначала проверяю базовый случай: если узел null, просто выхожу. Иначе рекурсивно вызываю traverse для левого ребёнка, потом добавляю значение текущего узла в result, потом рекурсивно вызываю traverse для правого ребёнка. В основном методе вызываю traverse(root, result) и возвращаю result. Список в Java передаётся по ссылке, поэтому все добавления из вспомогательного метода видны в основном - ничего возвращать из traverse не нужно.



Алгоритм работает так: обход inorder означает порядок «лево -> узел -> право». Рекурсия естественно это обеспечивает - мы полностью заканчиваем левое поддерево, прежде чем трогать сам узел, и полностью заканчиваем правое после. Для любого узла все значения левого поддерева оказываются в списке раньше его собственного значения, а правого - позже, что и требуется.



Временная сложность - O(n), где n это количество узлов. Метод traverse вызывается ровно один раз на каждый узел, и внутри каждого вызова выполняется O(1) работы: одна проверка на null, одно добавление в список и два рекурсивных вызова (они считаются отдельно для детей). Итого n вызовов умножить на O(1) даёт O(n). Список result занимает O(n) памяти, но это выходные данные, а стек рекурсии занимает O(h), где h - высота дерева.



Улучшить время нельзя - O(n) это минимум, ведь каждый узел нужно посетить хотя бы раз. Единственное реальное улучшение - итеративная версия с явным стеком (Deque), которая защищает от StackOverflowError на очень глубоких деревьях. У неё та же сложность O(n), но для учебных целей рекурсивная версия понятнее, а при ограничении в 100 узлов рекурсия абсолютно безопасна.
